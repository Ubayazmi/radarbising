# Supabase Migration Guide — Radar Bising

> **Purpose:** How to add, review, and deploy database schema changes using the Supabase CLI migration system.
> **Source of Truth:** `supabase/migrations/`
> **CLI Reference:** https://supabase.com/docs/guides/cli

---

## 1. Architecture Overview

```
supabase/
├── config.toml              # Local project config (auto-generated by `supabase init`)
├── migrations/
│   ├── 20261117000000_init.sql   # Initial schema (applied once, tracked in history)
│   ├── 20261118000000_add_xyz.sql # Future changes — ONE FILE PER LOGICAL CHANGE
│   └── ...
└── seed.sql                 # Optional: local seed data (not pushed to remote)
```

- **`supabase/migrations/`** is the **single source of truth** for schema.
- Each file = one logical migration, named `<timestamp>_<description>.sql`.
- **Never edit an already-applied migration.** Create a new file.
- Applied migrations are recorded in the remote database table `supabase_migrations.schema_migrations`.
- Deployment: GitHub Actions workflow `supabase-migrations.yml` runs `supabase db push`.

## 2. Creating a New Migration

### 2.1 Local Development (Recommended)

```bash
# 1. Start local Supabase (requires Docker)
supabase start

# 2. Create a new empty migration file
supabase migration new add_column_example
# Creates: supabase/migrations/20261118123456_add_column_example.sql

# 3. Edit the file with your DDL
# 4. Apply locally to test
supabase db reset          # Re-applies all migrations from scratch (destructive!)
# or
supabase db push --local   # Applies pending to local

# 5. Test your app against local DB
# 6. When satisfied, commit the migration file
git add supabase/migrations/20261118123456_add_column_example.sql
git commit -m "feat: add xyz column to articles"
git push origin main
```

### 2.2 Direct File Creation (No Local Supabase)

If you don't have Docker/local Supabase, create the file manually:

```bash
# Generate timestamp: YYYYMMDDHHMMSS
date +%Y%m%d%H%M%S
# → 20261118123456

# Create file
touch supabase/migrations/20261118123456_add_column_example.sql
```

Then edit with your DDL. Use **idempotent patterns** where possible:
```sql
-- Add column (safe if already exists)
ALTER TABLE articles ADD COLUMN IF NOT EXISTS featured_image TEXT;

-- Add index
CREATE INDEX IF NOT EXISTS idx_articles_featured ON articles(featured_image);

-- Add trigger (use CREATE OR REPLACE)
CREATE OR REPLACE FUNCTION ...;
CREATE OR REPLACE TRIGGER ...;
```

## 3. Migration File Naming Convention

```
YYYYMMDDHHMMSS_short_description.sql
```

| Part | Format | Example |
|------|--------|---------|
| Timestamp | UTC `YYYYMMDDHHMMSS` | `20261118123456` |
| Description | lowercase, snake_case, concise | `add_featured_image_to_articles` |

Examples:
- `20261118123456_add_featured_image_to_articles.sql`
- `20261119080000_create_categories_table.sql`
- `20261120153000_add_foreign_key_articles_category.sql`

## 4. DDL Patterns & Best Practices

### 4.1 Adding Columns
```sql
-- Simple nullable column
ALTER TABLE articles ADD COLUMN IF NOT EXISTS featured_image TEXT;

-- Column with default
ALTER TABLE articles ADD COLUMN IF NOT EXISTS view_count BIGINT DEFAULT 0;

-- Column with constraint (PostgreSQL 12+)
ALTER TABLE articles ADD COLUMN IF NOT EXISTS status TEXT
  CHECK (status IN ('draft','published','archived')) DEFAULT 'draft';
```

### 4.2 Adding Indexes
```sql
-- Standard index
CREATE INDEX IF NOT EXISTS idx_articles_view_count ON articles(view_count DESC);

-- Partial index
CREATE INDEX IF NOT EXISTS idx_articles_published_featured
  ON articles(published_at DESC) WHERE is_headline = TRUE;

-- Unique constraint
ALTER TABLE users ADD CONSTRAINT IF NOT EXISTS uq_users_email
  UNIQUE (email);
```

### 4.3 Adding Constraints
```sql
-- Foreign key (PostgreSQL validates existing data)
ALTER TABLE articles
  ADD CONSTRAINT fk_articles_author
  FOREIGN KEY (author) REFERENCES users(full_name)
  ON UPDATE CASCADE ON DELETE RESTRICT;
```

### 4.4 Triggers & Functions
```sql
-- Use CREATE OR REPLACE for idempotency
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE TRIGGER trigger_articles_updated_at
    BEFORE UPDATE ON articles
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
```

### 4.5 Enum Extensions
```sql
-- Safe enum value addition (cannot remove values)
ALTER TYPE user_role ADD VALUE IF NOT EXISTS 'SuperAdmin';
```

## 5. Destructive Operations — Safety Gates

The CI workflow (`supabase-migrations.yml`) **detects and blocks** destructive operations unless explicitly confirmed.

### What counts as destructive?
| Pattern | Example |
|---------|---------|
| `DROP TABLE` | `DROP TABLE old_table;` |
| `DROP COLUMN` | `ALTER TABLE articles DROP COLUMN old_field;` |
| `DROP INDEX` | `DROP INDEX idx_old;` |
| `DROP TRIGGER` | `DROP TRIGGER trigger_old ON articles;` |
| `DROP FUNCTION` | `DROP FUNCTION old_func();` |
| `TRUNCATE` | `TRUNCATE TABLE sessions;` |
| `DELETE FROM` | `DELETE FROM articles WHERE ...;` |
| `ALTER ... DROP` | `ALTER TABLE articles DROP CONSTRAINT ...;` |
| `REVOKE` | `REVOKE ALL ON articles FROM writer;` |

### To run a destructive migration:
1. Add the destructive SQL in a **new migration file** (required).
2. Push the file to `main` branch.
3. Trigger the workflow **manually** with:
   - `dry_run: false`
   - `apply: true`
4. The workflow will show the detected destructive operations and **require the same inputs** as a final confirmation.

> ⚠️ **Never** edit an already-applied migration to add destructive ops. The history will show the old version; create a new migration instead.

## 6. Local Testing Without Docker

If you can't run `supabase start` (no Docker):

1. **Syntax check** the migration with `pg_dump` or a local Postgres if available.
2. **Review manually** — the CI will also run `supabase db push` in dry-run mode and report pending migrations.
3. **Test against staging** by running the workflow against a staging Supabase project (separate project).

## 7. Deployment Workflow

### 7.1 Automatic (Push to Main)
```yaml
# Triggers on push to main when supabase/migrations/** or config.toml changes
# Runs in DRY RUN mode only — reports pending migrations, does NOT apply.
```

### 7.2 Manual Apply (Production)
1. Go to GitHub Actions → **Supabase Schema Migrations** → **Run workflow**.
2. Select branch: `main`.
3. **First run:** `dry_run: true` (default) → review pending + destructive scan.
4. **Second run:** `dry_run: false`, `apply: true` → applies via `supabase db push`.
5. Workflow verifies by re-querying `schema_migrations` table.

## 8. Rollback Procedure

Supabase migrations are **forward-only**. To "rollback":

1. Create a **new migration** that reverses the change (e.g., `DROP COLUMN` for an `ADD COLUMN`).
2. Apply it normally.
3. Never delete applied migration files — they are history.

Example rollback migration:
```sql
-- 20261125000000_rollback_featured_image.sql
-- Reverts: 20261118123456_add_featured_image_to_articles.sql

ALTER TABLE articles DROP COLUMN IF EXISTS featured_image;
DROP INDEX IF EXISTS idx_articles_featured;
```

## 9. CI/CD Integration

### Required GitHub Secrets
| Secret | Purpose |
|--------|---------|
| `SUPABASE_ACCESS_TOKEN` | Personal Access Token from Supabase Dashboard (scopes: `database`, `project`) |
| `SUPABASE_PROJECT_ID` | Project ref from Supabase Dashboard → Settings → General |
| `DB_DSN` | PostgreSQL connection string (Direct, port 5432) |

### Vercel Environment Variables (for app runtime)
Set in Vercel Dashboard → Project → Settings → Environment Variables:
| Variable | Source |
|----------|--------|
| `SUPABASE_URL` | Dashboard → Settings → API |
| `SUPABASE_ANON_KEY` | Dashboard → Settings → API (anon public) |
| `SUPABASE_SERVICE_KEY` | Dashboard → Settings → API (service_role secret) |
| `DB_DSN` | **Transaction Pooler** (port 6543): `pgsql:host=aws-0-<region>.pooler.supabase.com;port=6543;dbname=postgres;user=postgres.<ref>;password=***;sslmode=require` |
| `SESSION_SECRET` | Generate: `php -r "echo bin2hex(random_bytes(32));"` |
| `UPLOAD_DRIVER` | `supabase` |
| `SUPABASE_STORAGE_BUCKET` | `radarbising-uploads` |
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |

## 10. Common Tasks Quick Reference

| Task | Command / Action |
|------|------------------|
| New migration file | `supabase migration new add_my_feature` |
| Apply locally | `supabase db reset` (full reset) or `supabase db push --local` |
| View local status | `supabase migration list` |
| View remote history | Query `supabase_migrations.schema_migrations` |
| Dry-run deploy | Run workflow with `dry_run=true` |
| Production deploy | Run workflow with `dry_run=false, apply=true` |
| Check DB schema diff | `supabase db diff --local` (requires local DB) |

## 12. Quick Start for New Contributors

```bash
# 1. Clone repo
git clone https://github.com/Ubayazmi/radarbising.git
cd radarbising

# 2. Install Supabase CLI
npm install -g supabase

# 3. Login (requires token)
supabase login

# 4. Link to remote project (requires project ref)
supabase link --project-ref <your-project-ref>

# 5. Create a migration
supabase migration new my_change
# Edit supabase/migrations/XXXXXXXXXXXXXX_my_change.sql

# 6. Test locally (if Docker available)
supabase start
supabase db reset

# 7. Commit & push
git add supabase/migrations/XXXXXXXXXXXXXX_my_change.sql
git commit -m "feat: my schema change"
git push origin main

# 8. Deploy: GitHub Actions → Supabase Schema Migrations → Run workflow
```
